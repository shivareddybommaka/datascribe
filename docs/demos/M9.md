# M9 demo — Notifications + dashboards

Account: `nova`. Repo root: `~/projects/datascribe`. Synthetic data only; every email goes to
Mailpit (http://localhost:8025), never to a real inbox. Design notes: D-090..D-097.

**DoD (§12): "All listed events send email + in-app notification".** 7 of the 11 §5.8 events do
today. The other 4 need M6 (see the last section).

| §5.8 event           | State                    | Raised by                                                     |
| -------------------- | ------------------------ | ------------------------------------------------------------- |
| case submitted       | done                     | `POST /cases/:id/submit`                                      |
| processing complete  | done                     | worker pipeline stage 7 (case reaches `in_review`)            |
| invoice issued       | done                     | one-off invoice, monthly invoicing run (API and worker)       |
| payment received     | done                     | payment webhook (succeeded)                                   |
| payment failed       | done (critical, no mute) | payment webhook (failed)                                      |
| lead assigned        | done                     | CRM lead create / edit with another owner                     |
| task due             | done                     | worker `tasks-due` job every 15 min                           |
| assigned to you      | **blocked on M6**        | helper `notifyAssigned` ready, needs `POST /cases/:id/assign` |
| QA changes requested | **blocked on M6**        | helper `notifyQaDecision` ready, needs the QA route           |
| approved             | **blocked on M6**        | helper `notifyQaDecision` ready, needs the QA route           |
| delivered            | **blocked on M6**        | helper `notifyDelivered` ready, needs the delivery step       |

Also built: muting (§5.8 AC, security and payment-failed notices can't be muted), the admin's
per-event switches (Settings → Notifications), editable email text per event (Settings → Email
templates), upload-scan, processing-failed and invite-accepted notices, and all four §5.9 dashboards.

The worker sends the emails (outbox every 10 s) and runs the task-due job, so keep it running.
Sign in with `SEED_USER_PASSWORD` from `.env`; staff accounts ask for an authenticator code
(first sign-in sets it up). Web: http://localhost:3010.

### Notifications

1. **Case submitted.** Portal (http://localhost:3010/portal) as `client.user@acme.example`: New
   case, fill in synthetic values, submit. In another browser profile sign in to the console as
   `case.manager@datascribe.example`: the bell shows "Case DS-… submitted". Mailpit has the same
   email for the case manager and `ops.manager@datascribe.example`. The subject carries the case
   number only, never the patient or matter name.
2. **Processing complete.** Upload a synthetic PDF to that case (portal case page). The worker scans
   and processes it; when the case reaches "In review" the summarizer (or the case manager) gets
   "Case DS-… is ready for review" in the bell and in Mailpit. The uploader also gets "Record checked"
   in the bell (email off by default for that type).
3. **Invoice issued.** Console as `finance@datascribe.example` → Finance → Invoices → New one-off
   invoice for Acme. `client.admin@acme.example` gets "Invoice INV-… issued" in the portal bell and
   in Mailpit.
4. **Payment received / failed.** As `client.admin@acme.example`, Billing → open the invoice → Pay by
   card. Without a Stripe key a "Simulated checkout" page stands in for Stripe; click Pay. The client
   admin and `finance@datascribe.example` get "Payment received". The simulated checkout can't fail
   a payment, so "Payment failed" is shown by the API test (`test/notifications.test.ts`).
5. **Lead assigned.** Console as `sales@datascribe.example` → CRM → open a demo lead → change the
   owner to the ops manager. `ops.manager@datascribe.example` gets "Lead assigned: …". Assigning a
   lead to yourself sends nothing.
6. **Task due.** As sales, add a task on a lead due later today. Within 15 minutes (the worker's
   `tasks-due` job) the task owner gets "Task due: …", once per task and due date.
7. **Mute.** Bell → "All notifications and settings": untick "Invoice issued: email". Issue another
   invoice: the bell entry appears, no email. "Payment failed" and "Password changed" are locked on.
8. **Admin switches.** Console as `super.admin@datascribe.example` → Admin → Settings →
   Notifications: untick an event's email to turn it off for everyone. The user's preferences page
   then shows it as switched off by an administrator.
9. **Edit an email.** Same Settings page → Email templates → pick "Notification: Invoice issued"
   (group "Notification emails"). Change the subject to `New invoice {{invoiceNumber}}`, click
   Preview (synthetic values, with the preferences line added below), Save template. The next
   invoice email uses it. Unknown variables such as `{{patientName}}` and a body without `{{link}}`
   are refused. Restore default puts the built-in text back.

### Dashboards

1. **Ops** — console as `ops.manager@datascribe.example` → Dashboards: cases by status, open and
   overdue, average turnaround, workload per summarizer; window 7 / 30 / 90 days. As
   `summarizer@datascribe.example` the same page counts only the cases they summarize or review.
2. **Sales** — as `sales@datascribe.example` (after `pnpm db:seed:demo`): pipeline value by stage,
   conversion and win rate, leads by source; window 30 / 90 / 365 days.
3. **Finance** — as `finance@datascribe.example`: MRR (US$1,998.00 for the two seeded firms) and
   subscriptions by status, invoices outstanding and overdue, revenue by client net of refunds.
4. **Client** — portal as `client.admin@acme.example` → Reports: Acme's cases by status, pages
   processed and spend (paid invoices net of refunds). As `client.user@acme.example` the same page
   counts only the user's own and shared cases and shows no spend (D-096). Harbor's admin never sees
   Acme's numbers.

Pages processed and spend stay at zero until a case is delivered and an invoice paid; delivery is
M6, so for now only the paid one-off invoice from step 4 shows up as spend.

## Waiting on M6

The emit helpers, catalog entries, templates and admin switches for these four events exist and are
tested (`apps/api/test/notifications.test.ts`, "M6 emit helpers"). M6 only has to call them, after
its own transaction commits, wrapped in `safeNotify` (call sites in the doc comments of
`packages/db/src/notifications.ts`):

- `notifyAssigned(prisma, caseId, userId, role, actorId)` from `POST /cases/:id/assign`, once per
  role whose user changed. Self-assignment is silent.
- `notifyQaDecision(prisma, caseId, approved)` from `POST /deliverables/:id/qa`, once per
  decision. Tells the summarizer and case manager.
- `notifyDelivered(prisma, caseId)` where the case becomes `delivered`. Tells the creator, the users
  it is shared with and the firm admins; deduplicated per case.

When M6 lands, add a step per event to the "Notifications" list above and an e2e that checks the
bell after QA approval and delivery.
